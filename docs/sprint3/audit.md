## Розділ 3. Очікувані 5 питань замовника до демо та відповіді команди

1. **Чому в журналі виконання висока частка відхилених кейсів (21 з 49, тобто ~43% Failed)?**
   * *Відповідь:* Основний фокус Спринту 3 було спрямовано на перевірку межевих значень, негативних сценаріїв та алгоритмів обчислення оцінок (BL-30, F-60). Виявлені дефекти допомогли локалізувати ключові ризики перед розробкою автотестів у Спринті 4[cite: 23, 24].
2. **Які дефекти є найбільш критичними для бізнесу і який їхній статус?**
   * *Відповідь:* Найбільш критичним є дефект **BUG-#11** (`severity:major`, `priority:P2`), де не обчислюється штраф 10%/добу за запізнення. Усі 22 дефекти детально задокументовані в GitHub Issues та готові до передачі в розробку[cite: 23, 24].
3. **Чому 2 тест-кейси мають статус `Blocked`?**
   * *Відповідь:* TC-012 заблоковано через BUG-#11 (неможливо перевірити обмеження штрафу 50% без базового розрахунку), а TC-030 — через відсутність плагіна цензурування стоп-слів у стандартному публічному Sandbox[cite: 23, 24].
4. **Як забезпечується ізоляція та незалежність виконання кейсів при погодинному скиданні demo?**
   * *Відповідь:* Кожен кейс починається з авторизації/відкриття сторінки та використовує унікальні ізольовані назви курсів і завдань із префіксом `ТЗ-`, що виключає каскадні падіння[cite: 23, 24].
5. **Чи пройшли звіти про дефекти у GitHub Issues внутрішнє рецензування?**
   * *Відповідь:* Так, усі 22 звіти прорецензовані Скрам-майстром Білогривим із внесенням позначки `Reviewer` та дати. Аудитор-опонент додатково відтворив 3 дефекти різних рівнів severity (#1, #9, #11) виключно за текстом у трекері[cite: 23, 24].
