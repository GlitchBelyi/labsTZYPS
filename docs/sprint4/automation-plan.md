## 1. Мета, обсяг і правила

**Мета.** Автоматизувати перевірку бізнес-логіки модуля `eduportal` v1 (юніт-тести JUnit 5) і кілька стабільних UI-сценаріїв demo (Selenium IDE → експорт, Selenium WebDriver), щоб у спринті 5 той самий набір перевиконати на v2 і побудувати журнал регресії.

**Правила для всіх авторів**

1. Очікуване значення беремо з SRS 1.1 і записуємо константою. Обчислювати його тією ж формулою, що в коді, заборонено (чек-лист 13.3, п. 8).
2. У `@DisplayName` є ID вимоги і правило: `@DisplayName("BL-30: запізнення 2 доби, 80 → 64,00")`.
3. Помилкові вхідні дані перевіряємо через `assertThrows(IllegalArgumentException.class, …)`.
4. Повторювані перевірки з різними даними — `@ParameterizedTest` (`@CsvSource`, `@MethodSource`).
5. Дробові значення — `assertEquals(expected, actual, 0.001)`; `assertAll` для кількох пов'язаних перевірок.
6. Тест незалежний: спільні дані створює `@BeforeEach`, статичних змінних зі станом немає.
7. Код модуля в `src/main/java` не змінюємо. Усі зелені й червоні результати фіксуємо як є.
8. UI-тести мають тег `@Tag("ui")`, запускаються командою `mvn test -DexcludedGroups=none`; локатори — за `id`/`name`, а не за текстом (мова demo нестабільна); очікування — `WebDriverWait`, жодних `Thread.sleep`.
9. Етика demo: тільки обліковий запис `student`, один вхід на тест, без циклів і масових запитів, без зміни паролів і видалення чужих записів.

## 4. Розбіжності, ризики й питання замовнику

### R1. Формат результату BL-80: SRS 1.1 проти README модуля

SRS 1.1 (BL-80) вимагає список українських рядків: «Невірний код зарахування», «Поза періодом зарахування», «Немає вільних місць», «Не складено передумовний курс». README модуля v1 описує коди `KEY`, `PERIOD`, `CAPACITY`, `PREREQUISITE`. Якщо код повертає коди, тести Мележика (за правилом 1) впадуть, і це **дефект модуля v1** (відхилення від SRS 1.1). Пропонована оцінка: Severity — Normal, Priority — P3 (BL-80 має пріоритет Medium; впливає на GUI-65, але зарахування не блокує). Рішення КТ: тест лишається за SRS, окремий Issue (#38), питання Q1 замовнику.

### Правило тріажу, прийняте КТ (діє на спринт)

| Ситуація | Рішення |
|---|---|
| Код відхиляється від чіткої вимоги SRS 1.1 (High) | Дефект модуля. Major / P2, якщо спотворюється оцінка чи доступ до курсу; Normal / P3 в іншому разі |
| Код відхиляється від чіткої вимоги SRS 1.1 (Medium) | Дефект модуля. Normal / P3 |
| Вимога неоднозначна, код має одне з можливих трактувань | Не дефект. Питання замовнику, тест позначено «інтерпретація» у `@DisplayName` |
| Тест красний через тест-дані автора | Виправляє автор, Issue не створюємо |
| Спірне між автором і рецензентом | Аргументи 15 хв, потім рішення КТ (статут, 1.3) |
| Дефект підтверджується в `v2` у спринті 5 | Статус reopened, нового Issue не створюємо |
